# 번역 캐시·공시 HTML·RAG 계약

개발 브랜치 기준, 2026-09-03. 한국어 원문을 사실의 기준으로 유지하며 결정론적 영문 대체문을 만들지 않는다.

## 생성과 저장

- 제목: 수집 직후 고유 제목을 gpt-5-nano로 비동기 번역한다. 최대 5건을 점유하되 각 제목은 별도 요청으로 병렬 처리해 생성 실패가 다른 제목으로 전파되지 않는다. 정규화 제목 해시로 공유하며 임의 영문 조립이나 원문을 영어 완료로 저장하지 않는다.
- 뉴스: 최초 호버·상세 요청에서 news-bilingual-v1 공유 작업 하나를 등록한다. EN/KR 요청 모두 동일 원문 해시의 en 작업을 사용한다.
- 뉴스 한 번의 생성에 원문 기반 EN/KR What/Why/Impact와 영어 문단 번역을 포함한다. 문단 ID·개수·순서·금액·영어 필드를 검증한다.
- 검증된 양언어 요약을 PROCESSING 결과에 먼저 저장한다. summaryReady와 bodyReady로 부분 완료를 구분한다. 완성되지 않은 JSON이나 부분 문장은 노출하지 않는다.
- 완성 결과는 what/why/impact 및 각 _ko 컬럼에 따로 저장한다. 언어를 바꾸어도 추가 생성하지 않는다.
- 같은 원문으로 EN/KR이 모두 완료된 news-narrative-v12 캐시는 재사용한다. 한 언어만 존재하는 구버전 캐시는 새 양언어 계약으로 한 번 생성될 수 있다.
- 공시: 최초 상세 요청으로 섹션별 작업을 등록하고 전체 사용자에게 공유한다. 중첩 표의 번역 입력은 원본 HTML에서 자기 셀의 내용만 추출한다. 저장된 RAG 섹션과 인용 ID는 변경하지 않는다.
- 모델의 기관명·부서명·짧은 라벨 복사 오류는 프롬프트와 영문 스키마 제약으로 방지한다. 실패 결과는 대체 번역으로 저장하지 않는다.
- 공시 요약은 filing-summary-v3에서 한·영 세 필드를 함께 생성한다. what/why/impact는 영어, whatKo/whyKo/impactKo는 한국어이며 V59로 별도 저장한다.
- 요약 길이를 맞추기 위해 문장을 자르지 않는다. 법 조항·수량·복합 금액 단위를 구분하며 한국어 요약은 원문의 한국어 금액을 보존한다.

## API·화면

| API | 계약 |
| --- | --- |
| GET/POST /api/v1/news/{id}/translation?locale=en 또는 ko | 하나의 공유 작업, 선택 언어의 요약과 생성 상태 |
| POST /api/v1/disclosures/{receipt}/translation | 현재 문서의 섹션 작업 일괄 등록 |
| GET /api/v1/disclosures/{receipt}/translation | 문서별 원본 구조의 번역 HTML, total/ready/failed |
| GET/POST /api/v1/disclosures/{receipt}/sections/{section}/translation | 섹션 공유 캐시 조회·등록 |
| GET/POST /api/v1/disclosures/{receipt}/insight | 한 번 생성한 양언어 What/Why/Impact |

뉴스 기본 카드에서 캐시가 없으면 호버 안내를, 요청 이후에는 스켈레톤을 표시한다. 검증된 요약은 본문 완료를 기다리지 않고 폴링으로 갱신한다. 공시 영어 화면은 행렬을 새 표로 만드는 대신 원본 HTML의 텍스트만 바꾼다. rowspan/colspan·표 구조는 유지하며 미완료 셀은 선택할 수 없는 자리표시자로 둔다.

번역문은 HTML로 실행하지 않고 텍스트로 삽입한다. 원문 HTML도 서버 허용 목록으로 정제하며 원문 내용과 섹션 대응이 틀리면 실패로 처리한다. 한국어를 영문 화면의 폴백으로 넣지 않는다.

채팅 선택문은 질문 문자열과 별도로 저장한다. 공시는 현재 섹션 ID와 선택문이 함께 필요하다. 뉴스는 섹션 ID 없이 기사 원문 또는 현재 원문 해시의 READY 영어 본문과 선택문을 대조한다. 요약만 완료된 캐시·다른 기사·이전 원문은 인정하지 않으며 새 번역을 요청하지 않는다. 선택 주변 문맥은 최대 4,000자로 보존하고, 근거 길이를 제한할 때 JSON 자체를 절단하지 않는다. 다른 문맥은 선택 필드를 받지 않는다.

V61은 뉴스의 텍스트 단독 선택을 허용한다. 공시의 섹션·선택 쌍은 애플리케이션에서 검증한다. 롤백 시 확장된 DB 제약을 유지하며, 뉴스 선택이 저장된 상태에서 이전 제약을 무조건 복원하지 않는다.

V62는 생성 언어 정책을 저장하며 V63은 `auto`를 추가한다. 새 채팅과 공시 질문은 현재 질문의 언어로 답한다. AI 서비스가 인용문·URL을 제외한 질문과 혼합 문장의 종결 표현을 로컬 판정하고 EN/KR 중 한 스키마만 모델에 제공한다. 근거·이전 대화·사이트 언어는 판정에 전달하지 않는다. 숫자·기호만 있는 질문은 영어를 사용한다. 언어 판정용 OpenAI 호출은 없다.

프론트는 `answerLocale`을 보내지 않는다. 구버전 요청의 en/ko 힌트는 호환 목적으로 받되 새 생성에는 반영하지 않는다. 같은 멱등 키의 질문·선택문 변경은 거절하며, 화면 언어를 바꾼 재전송은 기존 생성을 반환한다. 장애 재시도는 저장된 질문·정책을 유지한다. 이미 저장된 en/ko 작업과 답변은 변경하지 않는다. UI 언어 전환은 뉴스·공시 출처 버튼 제목에만 반영하며 과거 메시지·본문 번역을 재생성하지 않는다. 롤백 시 V62/V63 컬럼과 데이터를 유지하고 auto를 지원하는 AI 버전을 함께 유지한다.

## 동시성·실패

- PostgreSQL의 종류·해시·언어·정책 버전 유일 키, 행 잠금, SKIP LOCKED 점유와 Redis 잠금을 함께 사용한다.
- 온디맨드 작업은 뉴스 2개·공시 2개의 독립 실행 슬롯, AI 요청은 동시 8개로 제한한다. 긴 공시 배치가 뉴스 처리를 막지 않는다. 같은 원문·버전의 실패 복구 시 이미 검증된 부분 요약 캐시는 유지한다.
- AI 전체 생성은 세마포어 대기와 분할 작업을 포함해 180초, Backend 번역 연결은 210초, 생성 잠금은 240초, 작업 회수는 300초다.
- 공급자 SDK 자동 재시도는 사용하지 않는다. 뉴스 제목의 시간 초과·일시 연결 장애·요청 한도만 지연 후 총 3회 이내로 처리한다. 기본 지연은 각각 15초·15초·1분이고 시도 횟수에 따라 늘어난다. 출력 검증 실패·미완료 생성·크레딧 부족은 자동 재생성하지 않는다. 온디맨드 실패의 재등록 제한은 15분을 유지한다.
- 입력/출력 오류 하나로 모든 작업을 멈추지 않는다. 전역 쿨다운은 일시 장애 15초, 요청 한도 1분, 크레딧 부족 기본 15분이다. 병렬 실패가 더 긴 쿨다운을 단축하지 못한다.
- 채팅의 AI_INVALID_OUTPUT은 연결 장애와 구분하고 재시도 버튼을 제공하지 않는다. 실패 로그는 생성 ID·AI 요청 ID·상태·오류 종류로 연결하며 사용자 질문·모델 출력·인증 값은 기록하지 않는다.
- 재시도 없는 정상 경로와 별개로 서버 중단 후 임대 회수는 필요하다. 분산 장애 상황까지 공급자 호출의 절대 exactly-once를 보장한다고 표현하지 않는다.
- V60은 인명 Jo를 허용하면서 숫자 뒤 조·억 음역과 eok-won 등의 금액 단위를 차단하도록 DB와 애플리케이션 검증을 통일한다. 제목 묶음의 저장은 항목별로 실패 처리하며, 완료된 작업을 늦게 도착한 실패로 덮어쓰지 않는다.

## 공시 원문·RAG

원문 HTML과 한글 섹션·표를 Zstandard로 **무손실 압축**한다. 요약문으로 원문을 대체하는 압축이 아니다. 구버전 payload에 HTML이 없는 문제와 원본 ZIP에 이미 손상 문자가 있는 문제를 구분한다.

원문 RAG는 한글 청크와 고정 다국어 임베딩을 사용한다. 검색은 접수번호·문서 버전을 격리하고 답변의 인용 ID를 검증한다. 번역 캐시 장애와 RAG 검색은 분리한다.
API와 색인 작업자는 같은 모델 캐시 볼륨을 사용한다. API는 임베딩 모델 준비에 실패하면 정상 기동으로 표시하지 않는다.

HTML 백필은 html-backfill 전용 프로필로 수행한다. 기본 읽기 전용, Flyway·스케줄러·DDL 자동 변경은 비활성이다. 아카이브 경로·SHA-256·원문 해시·모든 가시 내용과 기존 섹션의 대응을 확인한 뒤 HTML만 추가한다. 텍스트 손상·구조 차이는 자동 통과시키지 않는다.

- 기본 100건, 실행당 최대 2,000건, after-id/before-id 범위와 since-date 필터.
- fetch-limit 기본 0, 최대 20건만 OpenDART/API 뷰어 재조회.
- 적용에는 apply=true, Hikari read-only=false, 새 절대경로 backup이 모두 필요하다.
- 적용 전 기존 압축 payload를 권한 0600 파일에 기록·동기화하고 CAS로 변경 여부를 확인한다.
- reparse=true를 명시하면 구조 오류를 새 v6 문서 버전과 새 섹션으로 복구하고 RAG를 재등록한다. 완료된 분류는 반복하지 않는다. 옛 payload는 이전 버전으로 보존한다. 기본값은 false다.
- 압축 payload가 없는 초기 자료는 reparse와 제한된 API 재수집을 함께 지정해야 새 원본 버전으로 복구한다. 옛 문서·섹션은 삭제하지 않는다.
- HTML-only 복원은 opendart-html-v4-restored-v5로 표기해 재파싱과 구분한다. v6는 브라우저가 해석하는 최종 HTML 트리에서 섹션을 추출하고 정제 전후 가시 내용의 보존을 검사한다.
- 빈 XML·문자 손상·구조 손실은 정상 원문으로 저장하지 않는다. 공식 DART 뷰어의 동일 접수번호·메인 문서로만 복구하며, 첨부 문서 이름을 추정하지 않는다.
- 분할 뷰어는 최초 표지 주소가 아니라 전체 목차 범위를 수집한다. 공식 목차의 상하위 관계를 따라 하위 항목은 중복 수집하지 않으며, 서로 다른 최상위 범위의 부분 겹침·읽지 못한 목차·크기 초과는 실패 처리한다. HTML 표를 유지하고 목차 및 개별 응답 원본을 ZIP의 .raw 항목으로 함께 보존한다.
- 이전에 뷰어로 수집했으나 현재 정상 OpenDART XML을 받는 경우도 동일 접수번호의 메인 문서임을 확인해 복구한다. 저장된 문서 이름과 이전 버전은 보존하며 다른 첨부 문서로 교체하지 않는다.
- 이미 파싱된 특정 문서를 공식 원문으로 재검증하려면 receipts와 force-fetch=true를 함께 지정한다. 최대 20개 접수번호·reparse·충분한 fetch-limit이 필요하다. 이 옵션 없이 전체 구버전 스캔을 다시 시작하지 않는다.
- 복구 원본은 html-repair/접수번호/내용해시 경로의 0600 파일에 추가한다. 기존 ZIP·이전 문서 버전은 덮어쓰지 않으며 같은 파일은 해시를 검증한다. 백업에는 이전 payload와 아카이브 목록을 함께 저장한다.
- V58은 동일 원문 해시·파서 버전의 재수집에서 섹션 ID를 유지하며, 파서 변경은 별도 버전으로 저장한다. 롤백은 이전 바이너리만으로 할 수 없고 이전 스키마·데이터의 함께 복원이 필요하다.

## 검증·운영

동시 EN/KR 최초 요청 32개, 캐시 재사용, 실패 재방문, 부분 요약, 표 병합셀·중첩 표·XSS·원문 불일치 회귀 테스트를 유지한다. 실제 운영 측정과 아직 미완료인 배포·백필·브라우저 검증은 PIPELINE_REINFORCEMENT_20260902.md에 기록한다.
