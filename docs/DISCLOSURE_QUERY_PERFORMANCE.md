# 공시 목록 조회 성능 개선

## 문제

`GET /api/v1/disclosures`는 화면에 필요한 행 수와 관계없이 공개 공시 전체에 `COUNT(*) OVER (PARTITION BY filed_date)`를 적용했다. PostgreSQL은 최신 5행 요청에서도 공개 공시 234,479행을 조회하고 날짜순으로 임시 정렬했다.

운영 서버의 개선 전 실행계획은 다음과 같았다.

- 실행 시간: 약 2.7초
- 처리 행: 234,479행
- 공유 버퍼 접근: 약 159만 건
- 임시 디스크 정렬: 약 9.4MB

공시 복구 작업이 같은 PostgreSQL을 사용하는 동안 이 전체 스캔이 API 응답 지연을 키웠고, 홈과 내 정보 페이지의 `Loading current data…` 노출 시간이 길어졌다.

## 개선

- 무필터·커서 목록은 `disclosure_display_order_idx` 순서로 최근 후보만 제한해서 읽는다.
- 최근 후보 하위 쿼리를 `LIMIT`과 `OFFSET 0` 경계로 유지해 PostgreSQL이 넓은 공시 행 전체를 먼저 조인·정렬하도록 실행계획을 바꾸지 못하게 한다.
- 제목 번역과 지원 종목 조건을 만족하는 행을 화면 요청 개수만큼 찾으면 조회를 종료한다.
- `filedDateTotal`은 현재 페이지 행 수가 아니라 해당 날짜의 전체 공개 공시 수로 유지하되, 반환된 날짜에 대해서만 계산한다.
- 종목 필터가 있는 요청은 전체 목록용 최적화 경계를 사용하지 않고 `disclosure_security_display_ready_idx`에서 해당 종목의 최신 공시를 직접 읽는다.
- 검색·종목·기간·종류·정정·커서 필터와 최신순 정렬 API 계약은 유지한다.

최초 개선안은 좁은 컬럼만 선택한 실행계획에서 약 2.6ms였지만, 실제 응답 컬럼을 모두 선택하면 PostgreSQL이 넓은 공시 행 전체를 다시 정렬해 운영 API가 약 0.4~0.5초 걸렸다. 이를 재발 방지 기준에 포함하고 최근 후보 수를 먼저 제한하는 2단계 조회로 보완했다. 동일한 실제 응답 컬럼 기준 실행계획은 약 7.3ms였고 공시 본문 스캔은 최근 128행에서 종료됐다. 종목 필터에 전체 목록용 경계를 그대로 적용하면 약 0.49초가 걸리는 것도 확인해 조회 경로를 분리했고, 전용 인덱스 배포 후 실제 API는 약 0.09~0.14초였다.

## 검증 기준

- 공시 목록 API 회귀 테스트와 전체 Backend 테스트를 통과해야 한다.
- 홈의 4건 요청과 기본 20건 요청이 최신순을 유지해야 한다.
- 첫 페이지뿐 아니라 커서 기반 다음 페이지도 최근 후보 제한을 사용해야 한다.
- 날짜별 총계가 현재 페이지 크기로 축소되지 않아야 한다.
- 운영 배포 후 반복 요청에서 5xx가 없어야 하며, 응답시간이 복구 작업과 동시에 안정적으로 유지되어야 한다.
